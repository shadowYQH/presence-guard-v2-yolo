# 人影守望 · Presence Guard v2（YOLO 版）

一个 Android 摄像头应用：画面里出现人时持续播放提示音。**不依赖人脸** —— 背对镜头、
侧身、戴口罩、蹲在桌下、只露出半个身子也能识别。全部推理在设备本地完成，
不联网、不录像、不上传。

本仓库是 **v2**：把 v1 的「ML Kit 姿态 + EfficientDet」双引擎换成**单路 YOLOv10n**，
推理层自己写，APK 从 56MB 降到 13MB。

> 完整设计、参数表、调参指南、踩坑记录：**[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)**
> 加速器选型与实测数据：**[docs/PERFORMANCE.md](docs/PERFORMANCE.md)**

---

## 为什么不用人脸

人脸检测在真实监控场景里失效得太容易：人背对镜头、低头看手机、戴帽子口罩、
距离稍远、光线偏暗，人脸模型就什么都给不出来。而这个应用的诉求是
「画面里有没有人」，主体是人，不是脸。

所以检测的是**整个人体**。

## 和 v1 的区别

| | v1 | v2 |
|---|---|---|
| 检测引擎 | ML Kit Pose（33 关键点）+ EfficientDet-Lite0，双引擎互补印证 | 单路 YOLOv10n（TFLite） |
| 推理框架 | `tensorflow-lite-task-vision` + `mlkit-pose-detection` | 只有 `tensorflow-lite`，解码自己写 |
| 输入尺寸 | 320×320 | **640×640** |
| 误报压制 | 空间：两个引擎在同一位置互相印证 | 时间：同一位置连续命中 N 帧 |
| 单帧推理 | ~80ms 检测 + ~70ms 姿态 | ~190ms（一路全包） |
| APK | 56 MB | **13 MB** |

换掉的理由：v1 的天花板是 EfficientDet-Lite0 @320 的能力边界，远处 25~45px 的目标
缩放后特征不足 10px，怎么调参都出不来。要突破只能上 640 输入的 YOLO 类模型，
而 YOLO 的 TFLite 导出没有 metadata、`task-vision` 不认、也不接受量化模型，
所以推理层只能自己写（`YoloDetector.kt`，约 650 行）。

代价：没有关键点，就没有骨架可视化。换来的是更简单的链路和更好的小目标召回。

## 判定链路：四层

```
每帧图像
   │
   └── YOLOv10n ──► 候选框 + 分数
             │（整帧 / 瓦片滚动 / 选区放大，三选一）
             │
             ├── ① 形状门限（宽高比只拦离谱的，不加朝向约束）
             ├── ② 面积门限（双向：太小=噪点，太大=贴镜头/纯色面）
             ├── ③ 小目标轨迹持久化（低门槛 + 同位置连续命中 N 帧）
             └── ④ 滑动窗口投票 + 迟滞 → 提示音
```

1. **形状门限**：宽高比 `高/宽 ∈ [0.15, 12]`。只拦横得像横杆、竖得像立柱的框。
   人躺着、坐着、只露一条腿都在区间内。v1 的教训是别在这里加「人必须竖直」这类
   朝向相关约束 —— 俯拍和侧躺会全废。

2. **面积门限（双向）**：太小丢弃（远处噪点、墙角）；大到覆盖 94% 画面也丢弃
   （贴镜头、纯色墙面被当成人）。

3. **小目标轨迹持久化**：面积占比过小的候选不要求单帧高分（离得越远原始分天然越低），
   改成「低门槛 + 同一位置连续命中 N 帧」。真人会一直待在那儿，
   而噪点、树影、晾的衣服是随机的，不会连续命中同一位置。
   **用时间证据换空间置信度** —— 这是 v2 补小目标召回的核心。

4. **时序投票 + 迟滞**：最近 8 帧至少 4 帧命中才进入；连续 12 帧无目标才退出。
   进入阈值 0.46 高于退出阈值 0.32，人站在阈值边缘时不会反复报警。

## 三个关键设计

### 1. 三条检测路线，省算力的核心

一条路线不可能同时做到「便宜」和「看得清远处」，所以拆成三条，**按场景互斥选择**：

- **整帧**（默认）：每帧一次 640×640，覆盖近处大目标，成本固定 190ms；
- **瓦片**（按需）：画面切网格，每帧只滚几片。默认关闭，灵敏度拉到「灵敏」才开一片；
- **选区**（用户画了多边形）：只在这些区域判定，并把选区裁出来**放大送检**。

> 为什么不能靠提高采集分辨率：模型输入恒为 640×640，缩放会把分辨率增益完全抵消。
> **唯一有效的手段是缩小送进模型的视野。**

### 2. 多边形选区 + 多个小选区

用户可以在预览画面上点几个点围成一个多边形，程序只在这个多边形里判定，
并且把选区裁出来放大送检 —— 相当于给画面加了一台长焦。实测一个 40px 的人
在整帧里缩到 640 后只剩 17px，裁掉选区后能变成 90px，识别率差一个数量级。

**可以同时用多个选区**，数量不限。实际建议 2~4 个：每帧只轮转扫 2 个，
选区越多，单个选区被扫到的间隔越长，确认有人所需的绝对时间越久。
全画面铺满小选区等于放弃性能优势，不如直接用整帧 + 瓦片。

选区模式实测 **~7.5fps**，比整帧模式的 4.2fps 快一倍 —— 因为只扫画面的一小块。

### 3. 预览功耗治理

预览（相机输出流 + 显示合成）约占 **13~17% 单核**，熄屏后没人看画面，这部分应该归零。

只调 `Preview.setSurfaceProvider(null)` **不会归零** —— 用例还绑在相机上，
那条输出流照样在跑。必须把 Preview 从 `bindToLifecycle` 的用例列表里去掉。

另外在 MIUI 上有个坑：熄屏时 Activity 只走到 `onPause`，`onStop` 经常不触发。
所以摘预览由 `onPause`/`onResume` 驱动，再加 `ACTION_SCREEN_OFF` 广播兜底。
只在 `onStop` 里做的话，熄屏后 CPU 会一直停在 130% 下不来。

检测本身在熄屏后继续跑（前台服务 + `WAKE_LOCK`）。

## 实测性能

设备：小米 M2007J1SC（骁龙 865 / Adreno 650），Android 13，分析流 1080×1440。

| 模式 | 帧间隔 | 帧率 |
|---|---|---|
| 整帧（默认） | ~240ms | **≈4.2fps** |
| 选区 1 个 | ~133ms | **≈7.5fps** |
| 省电模式 | ≥200ms | 5fps 上限 |

| 后端 | 单帧推理 |
|---|---|
| **CPU（XNNPACK，4 线程）** | **191ms** ← 采用 |
| CPU（关 XNNPACK） | 836ms |
| NNAPI | 编译失败 |
| GPU（OpenCL） | 不可用，0 个内核 |

GPU 和 NNAPI 都跑不起来，原因是这个混合量化模型里的 int8 张量不被支持。
既然一个内核都上不了，GPU 依赖已经从项目里移除（省 13MB）。
详细日志见 [docs/PERFORMANCE.md](docs/PERFORMANCE.md) 第 2 节。

## 安装

```bash
export JAVA_HOME=~/.jdks/jbr-21.0.11
gradle :app:assembleRelease
# 产物：app/build/outputs/apk/release/app-release-unsigned.apk（13MB）
```

签名后安装，或直接装 debug 包：

```bash
gradle :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

环境：JDK 21、Gradle 8.11.1、AGP 8.5.2、Kotlin 2.0.21、minSdk 26、仅 arm64-v8a。

## 使用

1. 授权相机与通知权限
2. 手机架好对准要看的区域，点「开始」
3. 三档灵敏度：「灵敏 / 均衡 / 稳重」，默认均衡
4. 想要更高召回和更低功耗 → 点「选区」，在画面上点几个点围出区域（点回起点闭合）
5. 「焦段」循环变焦 1x→2x→3x→5x→8x（有多颗后置相机的机型才会出现镜头切换）

### MIUI / 国产 ROM 必做

否则熄屏几分钟后会被系统杀掉：

- 设置里允许**自启动**
- 电池优化设为**无限制**
- 在任务卡片上**锁定后台**

## 已知限制

1. 单帧上限 4.2fps。YOLOv10n @640 在 865 上就是这个水平。
2. 没有硬件加速（GPU/NNAPI 都不可用，见上）。
3. **黄昏 / 逆光下的小目标召回有限**。实测那张黄昏车站广场样图（目标 20~40px），
   分数只有 0.26~0.29。这不是参数问题，是模型能力边界。
   真实场景里人占屏 100px 以上时稳定在 0.7~0.85。
4. 多数机型只暴露 1 颗后置相机，此时「焦段」按钮自动隐藏。
5. 选区越多，单个选区的判定越慢。
